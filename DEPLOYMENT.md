# Deployment

1. Open a GitHub pull request and review the diff, tests, and any pending migration. Build with Node.js 22.13 or newer and the lockfile via `npm ci`. The GitHub **Verify website** workflow runs the isolated database fixture and checks generated route assets and indexing for Windows, hosted preview, and hosted production builds.
2. Configure the Vercel project with the Vite preset and tracked `vercel.json`. It builds `dist/` using `npm run build:hosted`. Connect Preview to a development Supabase project. Follow the [hosting guide](docs/hosting.md) for migration, staff setup, and secure redirect and recovery configuration.
3. In each Vercel environment, set `VITE_SUPABASE_URL` to the project origin and `VITE_SUPABASE_PUBLISHABLE_KEY` to the matching publishable key. Set Production `SITE_ORIGIN` to the canonical HTTPS origin. Configure optional Google review URLs only for the verified listing. The catalog shows an unavailable state when the Supabase pair is absent. Invalid or partial values fail the hosted build.
4. Verify public routes, direct product refresh and 404s, preview noindex, mobile layout, keyboard navigation, Maps and WhatsApp, and staff access. Use the preview for invite, recovery, MFA, disabled and non-staff accounts, image lifecycle, and concurrent updates. Check draft and archived products and private stock from a signed-out browser.
5. Verify business details and data with the owner. Use production credentials only in the approved environment. Apply database migrations only after review and backup. Apply `202611210003_repair_gallery.sql` before using the hosted repair gallery controls. Verify a consented repair entry in Preview and confirm legacy completed-work entries still display. Obtain explicit owner approval before publishing to production.
6. After release, verify the canonical domain, sitemap, indexability, access restrictions, and public product/image availability. Review function and Supabase logs for failures. Roll back frontend defects to the previous known-good deployment. Database changes require a separate recovery plan.

The [release audit](docs/release-audit.md) tracks remaining verification. No live backend changes are required to run the local QA fixture.
